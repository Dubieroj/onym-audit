The Onym audit seat, checked in five minutes

Audit.md described the audit seat and said no concrete profile existed. This submission is that profile, two independent verifiers, a conformance suite, and a running seat anyone can take — from their browser, with an Onym identity.

I.

Start here

Three paths, a few minutes each. Everything you do is signed in your browser and verified by the code in the repository.

  1. Open the app, create an auditor identity (twelve words — the key is derived exactly as the Onym apps derive it), register, and examine something: a Discovery catalog such as https://foldy.io/audit/discovery/manifest.json runs the 42-check suite. Sign and publish; the Library verifies it in your browser and shows its Stellar anchor.
  2. Switch to the Customer tab with a second identity, order an audit from the auditor you just created, then take the order as that auditor and sign: the published order carries three signatures — subject, sponsor, auditor.
  3. From the repository, run the tests and the whole attestation lifecycle in one command:
terminal
git clone https://github.com/Dubieroj/onym-audit && cd onym-audit
go test ./...                                   # 97 tests and subtests, incl. byte-pinned fixtures
node tools/verify-js-test.mjs                   # the independent browser verifier, same vectors
node tools/onym-id-test.mjs && node tools/stellar-test.mjs
tools/sandbox.sh                                # issue, reply, order, supersede, revoke, byte drift
go build -o bin/onym-audit ./cmd/onym-audit
bin/onym-audit conformance-discovery -manifest https://foldy.io/audit/discovery/manifest.json

What was built

Each result names its state honestly and links to its code.

01 · specification

The first implementation profile for Audit.md

Audit-Static-Ed25519: every document of the seat, canonical signing, serving and freshness, relying-client verification, error mapping, fixtures and gaps — and §12 maps all nine acceptance criteria of Audit.md §16 to where they are met.

the profile audit/

02 · tested

Two independent verifiers, byte-identical to Onym's reference

A relying client in Go and another in the browser (WebCrypto), both proven byte-identical to the Rust reference onym-discovery on its own vectors, and both passing 34 pinned fixtures: 22 decision cases and 12 malformed documents.

fixtures/ verify.js

03 · works

A conformance suite for Discovery providers

42 checks, each citing its clause, run black-box against any provider's public bytes. It is the examination behind conformance attestations; the hub runs it for any auditor, and it applies only to Discovery providers.

scope conformance/discovery/

04 · live

The app: sign in with an Onym identity

Twelve words derive the auditor key exactly as the Onym apps do — the apps' own fixture phrase shows the same Stellar address. Auditor cabinet with a pipeline, customer cabinet, requests for proposals, and a library that verifies every verdict in the reader's browser. Only non-extractable keys are kept.

open the app library

05 · live

An audit hub: anyone can take the seat, anyone can order

Auditors publish signed, verdict-independent offers; orders are signed by subject and sponsor and countersigned by the auditor; the hub accepts an order only under an offer as published, and holds a fail until the order's embargo ends. Orders and requests follow the phrase to any device through an encrypted vault.

order page hub terms

06 · live · Stellar testnet

Registers anchored in Stellar

The digest of each auditor's register — attestations issued and revoked — is written to the auditor's own Stellar account after every change, signed in the browser. This seat's register is anchored; the library checks each anchor against a public Stellar node.

stellar.expert ↗ stellar/

07 · live

A Discovery catalog of auditors

Onym's default catalog lists four seat types and no audit seat; the Discovery contract keeps direct import open. This site's provider publishes the catalog onym-auditors — and it passes the 42-check suite: CLEAR.

provider manifest inclusion policy

08 · runs locally

An LLM examination engine and an offline console

Claude reads a repository at an exact commit through read-only tools; every finding must quote the lines it rests on, checked mechanically against the pinned bytes. The auditor keeps or drops each finding with a published reason and signs with a key that never leaves the machine.

III.

What is verified — and what is not

Verified

  • 97 Go tests and subtests; the browser verifier, identity derivation and Stellar encoding on the same vectors as Go.
  • Identity keys match the Onym apps' cross-platform fixture; the Stellar test network accepted the anchor transactions.
  • Every flow on the live site — register, examine, order, request, respond, publish, revoke, restore on another device — with test data removed afterwards.
  • This site's Discovery catalog passes the suite: CLEAR. Onym's own fails it on an expired snapshot — the published, Stellar-anchored attestation shows exactly why.

Not yet

  • Onym's apps do not read attestations yet: their contract screen still says “Pending — no audits yet”; a pull request needs the maintainer's consent.
  • Anchors are on the Stellar test network, like Onym's own contracts today.
  • Only one real Onym component is attested so far: its Discovery catalog.
  • One host; no reproducible build of Onym's contracts yet, so no build-provenance attestation for them.

Relationship

Built as a participant in Sobor 2026, a contest organized by the maintainer of the Onym reference components. Every attestation about an Onym-operated component states this relationship.
